## Product Goal

生産管理担当者が、複数の受注について、工程順序・設備能力・納期を考慮しながら実行可能な作業スケジュールを作成・変更できる状態を目指します。

主な利用者は、従業員 100 名以下程度の受注生産企業で、生産計画を担当する 1〜5 名程度の生産管理担当者です。

## Target Company

- 従業員 100 名以下程度
- 顧客から受注した部品・製品を加工・組立する受注生産型の製造業
- 工場は 1 拠点
- 生産管理担当者は 1〜5 名程度
- 同一品番の繰り返し受注や、内示にもとづく先行生産が存在する場合がある
- 一部工程を外部企業へ委託する場合があるが、初期フェーズでは対象外

## Primary Persona

### 香山 仁美

- 42 歳
- 田崎製作所 生産管理課 課長
- 製造現場を経験後、生産管理へ異動
- 3 名の生産管理担当者をまとめながら、受注後の生産計画・工程調整を担当

### Problems

- 複数案件の工程順序、作業時間、設備の空き状況を見ながら日程を組むため、スケジュール作成・調整に時間がかかる
- 設備への負荷集中を事前に把握しづらい
- 納期変更、急ぎ案件、設備トラブル、現場遅延によって再調整が頻繁に発生する
- 営業から進捗・完了見込みを聞かれた際、製造現場へ都度確認しないと分からない
- 本来行いたい工程改善や品質保証との改善活動に時間を使いづらい

## Scope

### In Scope

- 受注
- 受注に必要な工程の設定・確認
- 工程順序
- 標準作業時間
- 作業区・設備
- 生産能力
- 設備・作業区への負荷
- 工程ごとの投入予定・完了予定
- 生産スケジュールの作成・変更
- キャパシティ超過の把握
- 最小限の作業進捗

### Out of Scope

- 見積管理
- 原価管理
- 売上・利益管理
- 需要予測
- 詳細な在庫管理
- 購買管理
- 複数工場間の調整
- 高度な自動最適化
- 詳細な帳票・バーコード印刷
- 外注工程の実運用

外注工程は将来要求として存在する。ただし、将来対応だけを理由に現在のモデルを過度に抽象化しない。

## Current Product Flow

1. 受注する
2. 見積・製造準備などの上流工程で、必要な工程情報がある程度決まる
3. 受注をシステムに登録する
4. 受注で使用する工程を設定・確認する
5. 各工程を作業区・設備へ割り当てる
6. 投入予定・完了予定を決める
7. 設備能力と他の受注の負荷を確認する
8. 必要に応じて日程を調整する
9. 作業を実行する
10. 進捗を確認し、必要に応じて再計画する

## Epics

1. 受注を管理する
2. 工程と作業条件を管理する
3. 生産スケジュールを作成・調整する
4. 作業区・設備のキャパシティを把握する
5. 作業進捗を把握する

## Initial Development Slice

最初の実装では、プロダクト全体を完成させない。

以下の 1 本のユースケースを中心に、要求からドメインモデル、DB、実装まで縦に通す。

> 課長が、工程と依存関係・加工時間が決まっている受注について、各工程に設備と開始日を指定してスケジュールを作成する。システムは設備ごとの工程の順番と 1 日の能力時間から、各工程が使う日と時間を計算する。依存関係が崩れた工程は警告で示す。

詳細と決めた経緯は [docs/design/scope.md](./docs/design/scope.md) と [ADR-0002](./docs/adr/0002-initial-scheduling-scope.md)、Use Case は [UC-01](./docs/design/use-cases/UC-01-create-schedule.md) を参照。

この Slice で扱うもの:

- 受注
- 工程と加工時間
- 工程の依存関係（合流・分岐あり。受注をまたがない）
- 設備と 1 日の能力時間
- 設備ごとの工程の順番と、そこから計算する各工程の日ごとの時間（日をまたぐ工程あり）
- 依存関係違反の警告（能力時間は常に超えない）

最初は扱わないもの:

- スケジュールの変更（Use Case として）
- 時刻単位の詳細スケジューリング
- 作業区
- 段取り最適化
- 作業者能力
- 外注
- 自動最適化・AI による提案
- 並列（依存先の一部完成で次工程を始める）
- 受注をまたぐ依存
- 納期チェック
- 実績収集の詳細
- 製品・工程・設備の登録画面（初期データで入れる）
- 権限

## Technical Stack

- Language: TypeScript
- Backend: Hono（Node.js）
- Frontend: React + Vite（SPA）
- Database: PostgreSQL
- ORM: Drizzle
- API の型共有: Hono RPC
- パッケージ管理: pnpm workspaces
- Test: Vitest

詳細は [docs/design/architecture.md](./docs/design/architecture.md) を参照。

認証、インフラ、デザインシステムなど、現在の設計学習に直接関係しない領域は原則対象外とする。

## Design Principles

- Requirement より先に DDD パターンを決めない
- Data Model から設計を始めない
- Domain Model と Data Model を区別する
- 現在の要求から必要な複雑性だけを導入する
- 将来必要になるかもしれない、だけを理由に抽象化しない
- Domain Rule / Invariant / Aggregate Boundary / Transaction Boundary を説明できることを重視する
- 実装は設計仮説を検証するために使う

## Current Unknowns

今後の設計で明確にする。

- 品目に紐づく標準工程と、受注で実際に使う工程の関係
- 作業区と設備の責務の違い（Initial Slice では設備のみ扱う）
- ~~設備能力をどの単位で定義するか~~ → 設備ごとの 1 日の能力時間（2026-10-04）
- ~~キャパシティ超過を禁止するか、警告のみとするか~~ → 登録時は超えないように計算し、後から超えた場合は警告（2026-10-04）
- ~~スケジュール変更時に後工程を自動で追従させるか~~ → 依存する後工程は自動で追従させず、警告で示す（2026-10-04）
- 複数担当者が同じ設備のスケジュールを同時変更した場合の整合性
