# Use Cases

生産管理担当者がシステムに対して行う操作を、1 ファイル 1 Use Case で書く。このファイルは一覧・書き方・候補の洗い出しをまとめる。

## 一覧

| ID                                  | 名前                   | 種類 | Slice   | 状態   |
| ----------------------------------- | ---------------------- | ---- | ------- | ------ |
| [UC-01](./UC-01-create-schedule.md) | スケジュールを作成する | 変更 | Initial | レビュー済み |

- 種類: **変更**（保存すると何かが変わる）/ **参照**（見て判断するだけ）
- Slice: どの Slice で追加したか（いまは `Initial`）
- 状態: **下書き** / **レビュー済み**

## この Step で Use Case を書く目的

1. **主目的: Domain Rule を見つける材料を作る**。業務ルールは「ある操作をしたとき」に効く。操作を区切っておくと、Step 2 で「この操作で何が起きたら業務上おかしいか」を 1 つずつ問える
2. **範囲を決める**。Slice に入る操作と入らない操作を、理由付きで切り分ける
3. **副産物: どこが複雑かの感覚をつかむ**。Decision と Constraint が多い Use Case は、業務の判断が詰まっている部分（Core Domain の候補）。ほぼ登録・参照だけの Use Case は、支える側（Supporting）の可能性が高い

Core Domain を正式に見極めるのはこの Step の主目的ではない。ただし、3 の感覚は Step 3〜4 でどこに設計の力を注ぐかを決めるときに使う。

## Use Case とは

Epic・User Story との違い:

| 粒度       | 何を表すか                                          | 例（別の題材: 図書館）                       | 置き場所     |
| ---------- | --------------------------------------------------- | -------------------------------------------- | ------------ |
| Epic       | 大きな目的のまとまり                                | 本の貸出を管理する                           | Notion PRD   |
| User Story | 利用者の要望（〜として、〜したい。なぜなら〜）      | 利用者として、本を借りたい。家で読みたいから | Notion PRD   |
| Use Case   | システムに対する 1 回の操作と、その入力・判断・結果 | 本を貸し出す                                 | このフォルダ |

Use Case は Step 2（Domain Rule）の出発点になる。「この操作のときに何が起きたら業務上おかしいか」を Step 2 で考えるので、操作の単位で区切っておく。

## どこまで書くか

**短くてよい。1 ファイル 1 画面（30〜50 行）に収まる量が目安。**

### 1 つの Use Case の大きさ

担当者が **1 回の作業で達成する 1 つの目的** を 1 Use Case にする。

- 大きすぎる: 「生産スケジュールを管理する」→ 複数の操作を含んでいる（これは Epic）
- 小さすぎる: 「設備を選ぶ」→ それだけでは業務の目的を達成していない（操作の 1 ステップ）
- 判断の目安: 終わったときに担当者が「よし、これは片付いた」と言えるか

### 書くもの

- Actor / きっかけ / 事前条件 / Input / Decision / Constraint（候補）/ Output
- 事前条件には「この Use Case を始める時点で何が存在しているか」を書く。登録系の Use Case を書かない代わりに、ここで前提を明らかにする
- 主な流れを 3〜7 行
- 例外・別の流れのうち、**業務ルールに関係するもの**（例: 能力を超えていたとき）
- 迷っていること

### 書かないもの

| 書かないもの                         | 理由                               | どこで扱うか       |
| ------------------------------------ | ---------------------------------- | ------------------ |
| 画面の配置・ボタン操作               | 業務の判断と関係ない               | Step 7（必要なら） |
| データ項目の一覧                     | Data Model に引きずられる          | Step 6             |
| ルールの詳細（強制か警告か、境界値） | Step 2 の仕事                      | `domain-rules.md`  |
| Entity / Aggregate などの名前        | 要求より先にパターンを当てはめない | Step 3〜4          |
| 入力ミス程度の例外（未入力など）     | 業務ルールの発見につながらない     | 書かない           |

## 進め方

### 1. 候補を洗い出す（30〜60 分）

1. **場面を書き出す**: README のペルソナ（香山さん）の困りごとと、Notion の Epic「生産スケジュールを作成・調整する」の「対象」を材料に、「どんな出来事が起きたときにシステムを開くか」を書く
2. **場面ごとに、画面でする操作を動詞で書く**: 1 つの場面から複数出てよい
3. **変更 / 参照に分ける**: 業務ルールが効くのは主に変更系
4. **Slice に入るか判定する**: 範囲外（時刻単位の計画、作業者、外注、自動最適化など）は下の「Scope 外」へ
5. **似たものをまとめて 3〜5 個に絞る**: 「きっかけ」と「結果」が同じなら 1 つにまとめる

### 2. 選んだものを 1 つずつファイルにする

`_template.md` をコピーして `UC-01-<kebab-case-name>.md` を作り、上の一覧に追加する。書き方の見本は `_example.md`（別の題材: 図書館）。

埋める順番の目安:

1. 名前（〜する）と概要 1 文
2. きっかけ → Output（始まりと終わりを先に決めると、範囲がぶれない）
3. 主な流れ（3〜7 行）
4. Input / Decision
5. Constraint（候補）と例外
6. 書いていて迷ったことは、決めずに「迷っていること」へ

### 3. レビューを受ける

各ファイルの「レビュー記録」に、指摘と対応を残す。

## 候補の洗い出し

思いつくものを全部書く（ファイル化する前のメモ）。

### 元メモ（2026-10-03）

> **UC-生産スケジュールを作成・調整する**
> 生産管理課の受注後の担当者は、受注した製品情報をもとに生産スケジュールを調整する。
>
> - Actor: 生産技術課 課長
> - きっかけ: 営業・事務が受注した製品情報を登録する
> - Input: 製品情報（図面、納期、数量、品名、図番、加工工程、顧客情報）
> - 主な流れ:
>   1. 事務が受注した情報をシステムに入れる
>   2. 入れたことを報告する（システム外でも良い）
>   3. 担当者はスケジュール未割り当てを確認し、スケジュールの詳細を組む
>   4. 詳細を組むときは、現在の区域とマシン、人の稼働率を見る

### 元メモを分けた候補

元メモには、Actor もきっかけも違う操作が複数入っていたため、操作ごとに分けた。名前は仮。

| 候補                                 | Actor          | きっかけ                                    | 種類 | 元メモの該当箇所   | Slice   |
| ------------------------------------ | -------------- | ------------------------------------------- | ---- | ------------------ | ------- |
| 受注情報を登録する                   | 営業・事務     | 受注した                                    | 変更 | きっかけ、流れ 1   | 範囲外? |
| 未割当の工程を設備と日付に割り当てる | 生産管理担当者 | 未割当の製造オーダーがある                  | 変更 | 流れ 3             | 範囲内  |
| 割当済みの日程を変更する             | 生産管理担当者 | 納期変更・急ぎ案件・設備トラブル（AI 補足） | 変更 | タイトルの「調整」 | 範囲内  |
| 設備の負荷を確認する                 | 生産管理担当者 | 割当・変更の前に空きを知りたい              | 参照 | 流れ 4             | 範囲内? |

### UC-01 以外の Use Case に関係するルール（2026-10-03 のメモから）

UC-01 には入れず、それぞれの Use Case を書くときに使う。

| ルール                                                                         | 関係する Use Case（仮） | Slice                       |
| ------------------------------------------------------------------------------ | ----------------------- | --------------------------- |
| 完了したスケジュールはずらすことができない                                     | スケジュールを変更する  | `scope.md` 軸 1 次第        |
| 完了していない工程はスケジュールを調整することができる                         | スケジュールを変更する  | `scope.md` 軸 1 次第        |
| 期限が切れた工程でも、完了するまでは勝手に消してはいけない。期限はラベル | 横断（Step 2 で扱う）   | 「完了」を扱うか次第          |
| スケジュールのある製品は削除することはできない                                 | 製品を削除する          | 範囲外?（登録系は事前条件） |
| 受注していない製品も登録できる（過去のものなど。ただし受注しているとも言える） | 製品を登録する          | 範囲外?（登録系は事前条件） |

（AI 補足）「完了」を扱うには、工程の進捗（完了したかどうか）を記録する必要がある。README の「最初は扱わないもの」に「実績収集の詳細」がある。

## Scope 外にしたもの

| 候補                     | 外した理由（2026-10-04、ADR-0002）                                         |
| ------------------------ | -------------------------------------------------------------------------- |
| 受注情報を登録する       | 事務の作業。UC-01 の事前条件として、初期データで入れる                     |
| 製品・工程・設備を登録する | 登録系はルールが少なく、Data Model から設計を始めることになる。初期データで入れる |
| 製品を削除する           | 登録系と同じ理由                                                           |
| スケジュールを変更する   | 作成（UC-01）でも設備の順番のずれと警告の論点が出るため、次の Slice へ     |
