# ADR-0002: Initial scheduling scope

- **Status**: Accepted（「ルールの強さ」の行は [ADR-0003](./0003-rule-strength.md) で置き換え）
- **Date**: 2026-10-04

## Context

- 当初の Initial Development Slice は「生産スケジュールを作成・変更する」で、スケジュール管理全体に近く、MVP にするには大きすぎた
- このプロジェクトの MVP は、売れる最小の製品ではなく、設計の論点（Invariant、Aggregate Boundary、Transaction / Concurrency）を検証できる最小の範囲である
- UC-01（スケジュールを作成する）を書く中で、工程の依存関係・設備の能力時間・日をまたぐ工程についてのルールが具体的になった
- 検討の経緯は `docs/design/scope.md` と `docs/design/use-cases/UC-01-create-schedule.md` にある

## Decision

Initial Slice を次の範囲にする。

> 課長が、工程と依存関係・加工時間が決まっている受注について、各工程に設備と開始日を指定してスケジュールを作成する。システムは設備ごとの工程の順番と 1 日の能力時間から、各工程が使う日と時間を計算する。依存関係や能力時間が崩れた工程は警告で示す。

軸ごとの決定:

| 軸             | 決定                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| Use Case       | UC-01（スケジュールを作成する）のみ                                                                    |
| 割り当てる資源 | 設備のみ（1 工程 1 設備）                                                                              |
| 時間の単位     | 日。加工時間が能力時間を超える工程は日をまたぐ                                                         |
| 能力           | 設備ごとの 1 日の能力時間                                                                              |
| 設備の上の順番 | 設備ごとに工程の順番を持ち、順番と能力時間から日ごとの時間を計算する                                   |
| 工程の依存     | 合流・分岐あり。受注をまたがない。依存先が全量終わってから始める（暫定で翌日から）                     |
| ルールの強さ   | 追加時は依存関係・能力時間を破らない。設備の順番のずれで後から破れた場合は警告にとどめ、保存は止めない |
| 後工程の追従   | しない                                                                                                 |
| 納期           | 扱わない                                                                                               |
| 前提データ     | 初期データ（seed）で入れる                                                                             |

## Alternatives

1. **当初の Slice のまま（作成 + 変更）**: 論点は多いが、範囲が大きく MVP にならない
2. **1 工程は 1 日に収まり、日の中の順番を持たない（日ごとの合計で見る）**: 最も小さいが、日をまたぐ工程という業務上の難所と、「どの工程が翌日に回るか」という順番を表現できない
3. **依存関係・能力時間を常に禁止する**: ルールは単純だが、1 工程の追加で他の受注の工程まで連鎖的に直す必要があり、運用が重い

## Trade-offs

- 利点: 依存関係違反を警告にしたことで、1 回の保存で全受注の整合性を保つ必要がなくなる。破れた箇所を AI が直し方を提案する機能を後から入れやすい
- 利点: 設備ごとの順番を持つことで、日の中で何時に終わるかが計算でき、将来の「同じ日に始めてよいか」の判定につなげられる
- 諦めたこと: 依存関係が破れたスケジュールを保存できる。正しさの一部を課長の判断に委ねる
- 諦めたこと: 1 つの工程を動かすと同じ設備の後ろの工程がすべて動く（受注をまたぐ）ため、他の受注の日程が変わる

## Consequences

- Step 2 で、強制する Invariant と警告でよい Business Rule を区別して扱う
- 設備の順番は受注をまたぐため、Step 4〜5 で「設備の順番」と「受注」のどちらで整合性を守るかが中心の論点になる
- 後回しにしたもの（並列、同じ日の開始判定、AI による提案）は `scope.md` に記録し、Step 8 の要求変更として扱う
